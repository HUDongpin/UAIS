# Session and shared-file reference

Read this reference when selecting responsibility labels or checking an actual shared-file overlap. The [main contract](../../AGENTS.md#scope-and-execution) defines task authorization: a feature or repair request includes its necessary supporting source, copy, data and focused tests unless the owner specifies narrower paths or exclusions.

S01-S25 are responsibility labels, not an approval chain. The table describes default specialization for parallel assignment planning; necessary supporting edits in an ordinary task follow task scope, not a per-role file whitelist. Credentials, publication, Git operations, independent signoff and explicit exclusions remain protected by the main contract. Coordinate only with a known active writer, a reserved surface or an actual overlapping assignment; do not invent an unavailable approver or launch agents just to satisfy a label.

`Available` is a planning label, not evidence that a file is idle. Inspect the relevant diff and supplied coordination records before writing. `Future` describes a planned surface, not creation authority or proof of absence. No row starts work automatically. Use one writer per file and preserve other sessions' logs. A current request can span responsibility labels without a second role-assignment ritual.

## Shared surfaces

The main shared surfaces are data (`src/data/uais.ts`, S08), bilingual copy (`src/i18n/copy.ts` and localization helpers, S09), design tokens (`src/app/globals.css`, S06), shell/layout/providers (S01), learning and chat pages (S03/S04), course plaza (S02), teacher pages (S05/S13), backend contracts (`src/app/api/`, `src/lib/server/`, S12), chat export helpers (`src/lib/chat-actions.ts`, S04), tests (S11), tooling/docs/package config (S10), build/release config (S22), assets/export (S24), environment configuration (S19), and release intake (S25).

- Feature tasks may change the directly relevant data section and add focused tests without requiring the owner to name each file or section. Preserve shared contracts and apply the main Quality Bar.
- For a known active writer or reserved file, coordinate before writing; absent that conflict, complete necessary work directly. Repository configuration and broad test architecture deserve careful review, but do not create a separate approval step merely because S10, S11, S12 or S22 is listed.
- Keep product assertions and independent QA/signoff distinct from implementation. An assignment to review, report, research or inspect alone does not authorize feature repairs.
- S19 owns authorized secret placement and redacted parity evidence, not provider business logic. S25 may inspect and recommend Git slices; Git mutation still requires authorization.
- Do not add permanent S26+ roles unless S10/S25 establish a durable uncovered need and the owner approves it. Temporary subtasks do not add permanent roles or enlarge task authority.
