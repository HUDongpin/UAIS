## Summary of work completed

- Added `src/lib/server/ai-request-rate-limit.ts`: an in-process fixed-window
  limiter supporting several windows per key, with `Retry-After` derived from the
  window that resets last, bounded key tracking, and env parsers that fail closed
  onto protective defaults.
- Wired the limiter into `POST /api/learning/chatroom`. The check runs after the
  app-session check and body parse but **before** the course-authorization store
  read, so a throttled actor costs neither a provider completion nor a
  persistence round trip.
- Rejected rounds return 429 with the route's existing body
  (`{ error, traceId, redaction }`), the `x-uais-trace-id` header, `cache-control:
  no-store`, and a `Retry-After` header.
- Refactored the route's logger into a shared structured emitter so throttles log
  the same `[learning-chatroom]` line at `warn` level, deliberately skipping
  `Sentry.captureException` (a throttled client retrying in a loop must not flood
  the error budget).
- Registered the three new env names in the B-21 env surface catalog, the example
  env template, and the env-surface doc.
- Excluded `.claude/**` from Vitest discovery, mirroring the existing ignore in
  `eslint.config.mjs`.

## Key decisions

- **Limiter key is the actor alone, not actor + courseId.** The check runs before
  course membership is verified, so a course-scoped key would hand any client a
  fresh budget for every `courseId` it invents. `courseId` still rides along on
  the throttle log event for diagnosis. Moving the check after authorization
  would allow course scoping but would let an unauthorized caller drive unbounded
  store reads.
- **Two windows, not one.** A per-minute window alone still permits ~8600
  rounds/day. The per-day window is what actually caps spend; the per-minute
  window is what keeps a burst from being felt.
- **A rejected round consumes nothing.** Otherwise a client hammering the short
  window would burn the whole day's budget without ever receiving an answer.
- **`0` and malformed limit values fall back to the default.** The only supported
  kill switch is `UAIS_LEARNING_CHATROOM_RATE_LIMIT_MODE=off`, so a typo cannot
  silently disable protection.
- Per-process scope: with N serverless instances the effective ceiling is
  `limit x N`. That converts "unbounded" into "bounded and small". A hard global
  cap needs shared storage (Redis/Postgres) and is a separate S12 decision.

## Risks

- Per-process counting under-throttles across a multi-instance deployment (see
  Key decisions). Documented, not mitigated.
- The per-day window resets from an actor's first round rather than at a fixed
  calendar boundary, so `Retry-After` on a per-day rejection can be most of a day.
  That is correct for the algorithm but is a blunt learner-facing outcome; the
  per-minute window is what learners will actually meet in normal use.
- Default limits (6/min, 120/day) are an estimate of ordinary classroom use, not
  a measured figure. They are env-tunable without a redeploy of code.

## Follow-up recommendations

1. **`/api/learning/ai-guide` should get the same limiter next - higher priority
   than the chatroom was.** It sits behind the identical auth path
   (`getUaisAppSessionUserFromCookieString` + `authorizeLearningAiGuideCourseAccess`),
   has no live-approval gate, and spends on **both** DeepSeek and DashScope/Qwen,
   including a multi-agent mode that calls both providers in one request. Qwen
   multimodal is the more expensive per-call surface in the project. Wiring cost
   is small: the limiter is already generic, but the route has no injectable
   `now()` dep, so one must be added for testability.
2. **`/api/ai/chat` is not the open wallet and can wait.** Live provider spend
   there requires `executionMode: "live"` **and** `liveProviderApproved: true`
   **and** a request header matching `UAIS_LIVE_AI_APPROVAL_TOKEN`, on top of
   `assertUaisAiAccess`. A deployed demo without that token provisioned cannot
   reach a provider at all. Worth adding for defense in depth if the approval
   token is ever provisioned in a deployed lane; not urgent otherwise.
3. Consider a shared limiter helper for the AI route family once a second route
   adopts it, so the window definitions and env-name convention stay in one place.
4. If the demo is ever exposed publicly, a per-process limiter is a floor, not a
   ceiling. Pair it with a platform-level (Vercel/WAF) request cap and, if spend
   must be hard-capped, a shared-storage limiter.
