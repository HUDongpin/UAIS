## Option A stop-condition check (idempotency)

Option A abandons a losing append, which is only safe if a late-landing write cannot
double-append. Confirmed against the current store:

- `appendLearningChatroomTranscriptMessages`
  (`src/lib/server/learning-chatroom-transcript-store.ts:250-257`) filters incoming
  messages against the ids the room already holds, so replaying the same ids appends nothing.
- Both write paths replace the whole snapshot, never a partial record: the local path is a
  temp-file write plus `rename` (`:552-578`), the external path an optimistic whole-database
  replace. There is no half-written message state a late append could resume into.

Residual caveat recorded below.

## Decisions recorded

- **Option A chosen** over Option B. Option B has a prerequisite the assignment itself
  flags: `LearningChatroomTranscriptRepository` exposes no `signal`/`timeoutMs` seam, so it
  would have to be widened first, and an injected repository short-circuits the external
  store entirely, so the abort behaviour Option B changes is not observable through the
  test seam at all. Option A keeps the store contract untouched and is fully observable.
- **Allowance kept at +3000ms** (cutoff ~53s), as specified. Both budget comment blocks were
  rewritten to state the same arithmetic (acceptance criterion 5).
- **409-retry interaction (criterion 6) is explicit and deliberate: not suppressed.** The
  retry either fits inside the remaining budget or the cutoff wins and the whole cycle is
  abandoned with it. Suppressing it separately would need the Option B seam.
- **GET limiter message is its own string**, not POST's. Everything else - status 429, body
  `{error, traceId, redaction}`, `retry-after` header, `cache-control: no-store`,
  `x-uais-trace-id`, the warn-level `phase: "rate-limit"` structured line with
  `actorId`/`rateLimit`, and the deliberate absence of `Sentry.captureException` - is
  identical to POST's. Telling a polling client to "wait before sending another message"
  would have been wrong, and the message is what lets an operator tell the two throttles
  apart in the logs. Nothing renders this string: `fetchChatroomHistory`
  (`learning-page-chatroom.tsx:917-945`) degrades any non-ok GET to "no stored history".

## Caveats recorded (Option A)

1. A losing append continues detached and may be frozen mid-write when the instance
   suspends. Safe only because appends are id-idempotent and both write paths replace a
   whole snapshot (evidence above).
2. When the cutoff wins, the receipt says `unavailable` while the detached append may still
   land. The field therefore means **"not confirmed within budget"**, not "not written".
   Nothing consumes it today; this is stated in the helper's comment block in the route.
3. Pre-existing and unchanged by this package: a late-landing detached write replaces the
   whole snapshot, so it can still lose a concurrent room's update. That is the snapshot
   store's ceiling, already listed as a Phase 2 risk in the group plan (§8, retry 4 / postgres
   escalation), not something this deadline introduces.

## Risks

- The GET limiter is in-process and per instance, so on a multi-instance serverless
  deployment the effective ceiling is `30 x instances` per minute. Same documented caveat as
  the POST limiter; a hard global cap needs shared storage and is a separate decision.
- A 429 on GET is currently invisible to the learner: `fetchChatroomHistory` treats any
  non-ok response as "no stored history", so a throttled poller would silently show an empty
  room. Harmless today (history is fetched once per room), but **Phase 3 must handle 429
  distinctly from a genuine empty room when polling ships** — keep the last good transcript
  and back off instead of blanking the thread.

  S10/S19 own that back-fill (plan §6). They are read only through
  `readLearningChatroomHistoryRateLimitConfig` and every one has a protective default, so an
